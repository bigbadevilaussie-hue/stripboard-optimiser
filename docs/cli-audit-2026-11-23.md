# Native CLI audit and optimisation groundwork — 23 November 2026

Scope: the standalone headless v5 Node CLI (`src/frontend/tests/solver/v5Solve.js`), native C annealer (`decode.c`), TypeScript finishing/selection (`autoLayout5.ts`, `layout2/finish.ts`, `layout2/chooser.ts`), desktop adapter, and the 80-run benchmark scripts. No changes to the native anneal algorithm, decoder scoring or normal finish selection were made in this audit. These changes do **not yet** establish faster per-seed solving or improved valid-result yield.

Related evidence: [native solver benchmarking](native-solver-benchmark-2026-11-23.md). The 80 saved runs were completed on the user's iMac, not in this environment.

## Baseline and priorities

- Eight groups, ten fixed seeds per group, 20k moves, 24 × 56 locked boards; one strict clean result out of 80. The MOTO and MOTOMIX sources differ beyond F1.
- Approximate mean of the eight per-group means: **1,391 ms solve**, **1,179 ms anneal**, therefore anneal is **~84.8%** of solve time. This is a ratio of aggregated means; it is not a direct measurement of the entire command's wall time. Routing can occasionally exceed one second.
- An independent Python recount of actual endpoint-column diagonal wires and positive-length collinear wire overlap matched all 80 harness results. Knife counts matched *stored cut-kind labels*; independent pin/net geometry has **not** been proved.
- Priority is a **physically valid, electrically correct, reproducible layout**, not a lower solver price or a faster invalid candidate. Native acceleration needs a controlled before/after comparison with validity and layout fingerprints.

### Strict CLI semantics

The existing solver output is intentionally unchanged when `--strict` is **not** specified. With `--strict 1`, the harness emits `strictValid`, `strictFailures`, `diagonalsActual` and `cliVersion: "v1.59-cli-audit"`.

The strict gate rejects layouts with:

- Nonzero `quality`, verified conflicts or incomplete nets, or reported geometry errors;
- Nonzero **column-changing wires** (historical vertical-only benchmark rule), truly slanted wires, or reported crossings. Strict diagnostics expose `diagonalsActual` (column shifts), `slantedWires` and `horizontalWires` separately;
- Solver issues, changed locked rows/columns, or moved/rotated locked components;
- Nonzero total `knife` when `--drilled 1` is requested;
- Nonzero positive-length collinear `stacked` wires when `--nostack 1` is requested.

Exit codes: **0** compliant (in strict mode) or ordinary successful solve (non-strict); **1** caught solver exception; **2** strict candidate rejected; **64** invalid CLI argument. The CLI still writes `--save` layouts on a strict rejection so an invalid board can be investigated. **This is a post-solve hard gate, not a promise that native placement/routing can always satisfy the rules.**

*Limits:* electrical verification and geometry checks still use existing harness helpers. The stack metric is collinear overlap, not a separately agreed, stricter same-hole construction rule. A knife is counted from `cut.kind`; forced vs avoidable knife cuts are different questions. This gate is not yet a substitute for comprehensive independent board/netlist validation.

### Geometry terminology correction

The existing 80-run CSV field `diagonals_actual` counted any **column change**. A horizontal wire (same row, different columns) was therefore counted as a 'diagonal'. In contrast, the harness `offAxis` field counts wires where **both row and column change**. This explains OFFAX0 being more common than DIAG0.

- **Column shift / historical `diagonals_actual`:** `from.col != to.col` (horizontal links AND true slants).
- **True slant / harness `offAxis`:** both row and column change.
- **Horizontal wire:** same row but different columns.

The prior benchmark's acceptance gate is therefore **vertical-wires-only**, not simply 'no diagonals'. The updated CLI, independent audit and future benchmark output now show the categories separately while keeping the original 80-run acceptance definition intact. Whether horizontal wires are acceptable in production remains a separate physical-rule decision.

### CLI profiling options

- `--move-summary 1`: one `moveSummary` object in the final stdout JSON: `attempted`, `mutateFailed`, `decodeFailed`, `rejected`, `accepted`, `sameBoard`, `newBest`, `byKind`. It uses the existing native move-log callback without writing per-move gzip files. **It still incurs instrumentation overhead** and is for profiling, not clean speed benchmarks.
- `--finish-trace 1`: lines prefixed `finishTrace ` on stderr, one for each finalist. Contains the chosen finish and both candidates' scores, `quality`, column shifts, true slants, horizontal wires, crossings, stacked, all knives, solver-classified forced/avoidable knives, and reported `eligible` for repair. A null router eligibility means the router has **no equivalent eligibility flag**, not that it was validated. The forced/avoidable classification here uses the solver's definition, so it is **not independent validation**.
- `STRIPBOARD_TIMING=1`: unchanged detailed phase metrics.
- `--movelog <dir>`: unchanged full proposal log for detailed move distributions, when needed.
- Native/strict opt-in flags are deliberately independent: `--native 1` chooses the native module; `--strict 1` controls the final exit status.

### Benchmark throughput

`python3 scripts/benchmark_drill_stack.py --jobs 4` now runs four *isolated processes* concurrently within each 10-seed configuration, preserving seed IDs, boards and move counts. Raising to 6 or 8 is possible if RAM/CPU allow. Runtime speedup is **not yet measured**. To avoid replacing original benchmark evidence, specify a fresh output directory for reruns.

## Claude's proposals: action / evidence needed

1. **Native early rejection before routing**: Potentially valuable, but not safe to enable without proving a true *lower bound for the current annealing energy at the current schedule weight*, and handling RNG draw order. Some native cost terms are assessed late, so an incomplete bound must never reject an actually acceptable move. First measure the proportion of rejected fully decoded proposals using `--move-summary`.
2. **Wasted proposal histogram**: Implemented as opt-in `--move-summary 1`. Compare mutate failures, infeasible decodes, rejected full decodes, and same-board acceptances. If failure dominates before decode, optimise mutation; if full-decode rejects dominate, investigate a provably safe partial decode bound.
3. **Parallel CLI benchmark**: Implemented in the Python runner. Native solver results should be compared by seed and fingerprint; measure wall-time separately.
4. **Finish both candidates**: The trace now identifies whether an acceptable repair lost to a noncompliant router. Do not change scoring or skip finalists before examining that evidence. `exactRepairMs` is available in the CSV; `exactBest` is OFF in this 80-run baseline.
5. **Micro-optimisations to libm/imported math**: Deferred; determinism and meaningful measured gain matter more than speculative nanoseconds.
6. **Locked-board repair limitations**: In `finish.ts`, the zero-mess channel insertion is gated on no locked parts; additional compaction/cleanup is also conditional. On the F1-locked 24×56 board, some finishing remedies are unavailable. The trace should separate *both candidates intrinsically invalid* from *a valid candidate lost on score*.

## v1.60 full-matrix finish audit (23 November 2026)

The CLI and desktop display versions are now **v1.60-cli-audit** and **v1.60-debug**, respectively. This is a **diagnostic release**. The default annealer, router, repair and final selection decisions are unchanged. The version bump does not claim faster native annealing or a higher strict-valid result rate.

### Findings used to decide the change

The user's four-seed profiling proved that **none of the four repaired candidates was eligible** and the router won all four. This did not support the earlier hypothesis that a fully compliant repair was routinely discarded because of the router/repair stacking-score asymmetry. The asymmetry is still present and is now explicitly measured, not patched on speculation. On locked boards, the zero-mess line/channel expansion passes may not be available. Consequently a full 80-case comparison is required to measure the decoder/finisher mismatch and the fraction of cases where **both** candidates violate physical requirements.

### New instrumentation

- `layout2/finish.ts` now returns `scoreTerms` for **both** candidates, showing `quality`, `overCap`, the finisher's historical `offAxis` **column-change count**, `crossings`, the **stacking penalty actually charged**, `mess`, `qualityCost`, `messCost` and `price`. The router reports `stacked: 0` *in its score terms*, despite possible stacked wires in its actual geometry. This preserves and exposes the existing scoring discrepancy.
- Router phase timers are active **only with** `--finish-trace 1`, measuring `initialRoute`, `fallbackRoute`, `compaction`, `insertWireChannels`, `repairSlantWires`, `freeLinePass`, `trim`, and `cutCleanupAndDrill`. They capture the 1552 routing spike's internal stages without changing the routing outcome. No repair work cap is imposed until those timings identify a safe place for one.
- The finish trace includes the full candidate boards **only in memory**; the CLI removes them before writing logs, independently rerunning the existing harness's `verify()`, `checkGeometry()` and `metrics()` on each. Each candidate gets `verification.compliant`, `failReasons`, `conflicts`, `incomplete`, `geometry`, `crossingsHarness`, and lock-preservation checks. The trace also reports `anyCompliant` and `selectedCompliant`.
- `--move-summary 1` now includes `percent` for outcomes (mutation failure, infeasible decode, full-decode rejection, acceptance and same-board). This is a histogram of *iterations*, not a timing profile; it adds overhead and does not justify a native speed claim.

**Important validation limits:** The trace verifies both candidates using the repository's **existing** electrical and geometry helpers, not an independently implemented netlist proof. Its `compliant` test intentionally follows the original 80-run **vertical-only** wire rule, including horizontal wires as prohibited. `finishRepair.ok` is a *different* internal eligibility condition and must not be confused with the CLI's full physical compliance check. Forced/avoidable knife counts use the existing `tidyScore` classification. None of these claims includes a stricter Route-Mate hole-based stack prohibition beyond the collinear overlap test.

### Full 80-run profiling, fingerprint gate, and output

`scripts/profile_native_cli.py` now runs **all 80 original combinations by default**, rather than just four seeds. It reads the original benchmark `comparison.csv`, verifies the input projects are still locked 24×56, snapshots `baseline_snapshot.csv` with SHA256, and launches isolated native processes. Results and errors go to `/tmp/stripboard_drill_stack_80/cli_profile_v160_full80/`. Original `comparison.csv`, original solved layouts and original benchmark config are not modified. A changed baseline file causes the profiler to refuse comparison.

Outputs:

- `results.json` — CLI summary, complete score terms, actual wire/cut/stacking counts, candidate-level validator outcomes, routing phase timings and per-move histograms.
- `finish_matrix.csv` — one row per original case, with both candidates' faults and score decomposition.
- A separate solved JSON and stderr log for every case (profile output only).
- Console summary by project/configuration: repair `ok` count; repair physically compliant; router physically compliant; either compliant; selected compliant; both fail; and compliant alternative lost. The strict-valid result and **each saved-board `sig`** are compared to the original 80-run CSV.

A fingerprint mismatch or strict-validity mismatch is an error, **not** a reason to update golden outputs silently. The profiler also reconstructs every reported candidate score from `qualityCost + messCost + price` and rejects missing terms or candidate verifier data. Full-matrix output includes per-run move percentages, repair eligibility and routing-subphase columns. Both profiling and benchmark runners cap native concurrency to the Mac's reported physical core count. An all-80 trace is instrumentation and validation, not a performance benchmark.

## Verified v1.60 full-matrix outcome and v1.61 desktop qualification fix (23 November 2026)

### Results supplied from iMac: 80/80 full-matrix profile

All original 80 `sig` fingerprints and original CLEAN verdicts match. The profile found **one compliant router**, **zero compliant repair candidates**, **zero repair candidates meeting their internal `ok` test**, **79/80 cases where both finishes violate the requested rules**, **zero compliant alternatives discarded**, and zero failed profile cases. This conclusively refutes the hypothesis that the router/repair score asymmetry is the **primary** cause of these 80 failures; the asymmetry itself remains real. All 80 final selections were routed, not repaired.

Across 1,600,000 moves, 1,072,704 were rejected after decoding (67.0%), 446,966 were classified as same-board (27.9%), 2,942 mutations failed and none failed decoding. Classifications count outcomes, not measured per-outcome CPU time. An optimisation that discards same-board genome drift is not automatically safe.

The phase timer isolated the routing spike to `repairSlantWires`: **98.6 ms mean, 1,307.3 ms maximum** versus **20.1 ms mean** for the initial route. These were four-worker contended measurements; a serial run is necessary before claiming any speed improvement or evaluating a work cap.

The underlying solver was not improved in this measurement: **1/80 compliance and 80/80 identical layouts**. The dominant remaining work is developing a native objective that jointly optimises electrical and physical validity, and profiling safe early rejection without silently changing seed outcomes.

### Newly discovered GUI tournament correctness defect

While cross-checking the result path, `desktop/src/stripboard_optimizer/solver/worker.py` was found accepting Pass 1 and Pass 2 finalists on **`quality == 0 && offAxis == 0`** plus optional board dimensions. That omits complete-net validation, conflicts, footprint geometry, cut style, stacking and some lock rules. It could label a layout VALID despite violating a requested construction rule. The Python `is_valid()` helper also checked only a subset of these metrics, and was not used for the two-pass qualifier path.

**v1.61-debug** corrects the standalone desktop integration:

- Desktop adapter passes `--strict 1` to the v1.60 native CLI for every seed and recognises exit **2** as a completed but **noncompliant** solve. Other nonzero exits are errors; malformed or missing strict verdicts are rejected.
- The GUI's Pass 1, Pass 2 and manual/full-auto finalist gates require `strictValid === true` and no `strictFailures`. Existing electrical, geometry, column-shift, lock, knife and stacking checks in the harness determine eligibility. Noncompliant layouts still produce internal diagnostics but do not become winners.
- Pass 1 prints aggregated top rejection reasons, so zero qualifiers have a concrete explanation.
- The de-duplication signature now includes **component positions/flexible ends/leads, cuts and normalized wire geometry**. Two physically different routed layouts are no longer falsely marked as duplicates just because the parts occupy identical locations.
- Tests in `desktop/tests/test_strict_qualifiers.py` verify fail-closed strict qualification, wire identity independence, and preservation of different wire/cut layouts.

**Intentional compatibility distinction:** Native CLI remains **v1.60-cli-audit**, since the same 80 results must remain fingerprint-identical. Desktop GUI label is **v1.61-debug** because qualification semantics changed. The desktop uses the historical **vertical-wires-only** rule when strict is enabled, which is stricter than merely forbidding genuinely slanted wires. That rule should be made user-configurable separately if horizontal jumpers are to be allowed.

**Important trade-off:** With drill-only and stack-off enabled, the original 80-run baseline contains **zero compliant layouts**. A strict desktop tournament can therefore report **zero qualifiers** until the solver actually finds compliant boards. This is accurate reporting, not an algorithmic regression or a claim that seed expansion solves the underlying problem. Native speed and layout quality are not yet improved in v1.61.

## Remaining correctness work

- Independently verify connectivity, pin transforms, cut physical geometry and hole-level wire clearance. Neither `Q0` nor our initial audit establishes these conclusively.
- Decide whether the user's specific stack and drill requirements are **hard mandatory**. CLI `--strict` applies a hard **accept/reject** gate; it does not yet guide annealing.
- Investigate the asymmetry in router versus repair candidate scores and eligibility, using the saved trace.
- Once baselines exist, test a physical-validity-first candidate chooser behind a flag, never as a silent change to working search.
- Only then consider native decoder early-reject optimisation with a golden regression set of fingerprints, strict validity counts and comparable performance measurements.

**Do not claim a solver-speed improvement based only on parallel benchmark throughput.** These changes improve debugging, throughput and failure transparency; the search algorithm still needs evidence-driven tuning.
